DeepEval · LLM Evaluation Curriculum

AI Evaluation with DeepEval

A 28-day course from your first LLMTestCase to evaluating RAG pipelines and multi-agent systems. Every day has two columns: CODE — what students build and run — and THEORY — what to explain before they touch it. Built to be taught straight from the notebook.ipynb in this folder.

Module 01 · Days 01–05

Foundations — the eval loop

Students learn why LLM outputs can't be unit-tested, meet the test case and the judge, and write their first G-Eval by the end of the week. The judge built on Day 3 is reused every day after.

DAY 01

Why evaluate, and the eval loop

Code

  • pip install deepeval in a fresh venv; pin the version for the whole course.
  • Set DEEPEVAL_TELEMETRY_OPT_OUT=YES and confirm the import prints a version.
  • Call any LLM API twice with the same prompt — show students the output differs.

Theory

  • Why unit tests fail for probabilistic outputs — assert answer == expected dies on day one.
  • The eval loop: dataset → metric → threshold → pass/fail → regression when you change the app.
  • Where DeepEval sits: deepeval vs RAGAS, LangSmith, promptfoo — open-source, judge-based, framework-agnostic.
DAY 02

LLMTestCase — the unit of evaluation

Code

  • Build LLMTestCase with input, actual_output, expected_output.
  • Add context and retrieval_context variants; print each field.
  • Load cases from a small JSON list — the first golden dataset.

Theory

  • Anatomy of a test case: which metric consumes which field.
  • Golden datasets — curated input/expected pairs that never leave the repo.
  • When expected_output is optional, and why some metrics never look at it.
DAY 03

Judges — the LLM behind the score

notebook · G-Eval section

Code

  • Wrap a Groq model with LocalModel(model="llama-3.3-70b-versatile", base_url=…) — the course judge.
  • Variants: OpenAI, Azure OpenAI, Gemini, Ollama — all through DeepEvalBaseLLM.
  • Set temperature=0 and call judge.get_model_name() to verify.

Theory

  • LLM-as-judge: a model that scores another model's output.
  • Judge consistency and bias — always temperature 0, log which judge scored which run.
  • Cheap judge vs capable judge: an 8B can score tone; factual correctness wants more.
DAY 04

Running your first evaluation

Code

  • evaluate(test_cases, metrics=[…]) with one metric on two cases — one passing, one failing.
  • Set threshold=0.5; read the pass/fail table and aggregate metrics.
  • Parse results.test_results and metric_scores as Python objects.

Theory

  • Every metric returns three things: score (0–1), reason, verdict.
  • Thresholds turn continuous scores into pass/fail — your product decision, not a default.
  • Reading the aggregate table: average score, pass rate, per-metric totals.
DAY 05

G-Eval — metrics you write in English

notebook · G-Eval section

Code

  • GEval(name, criteria, evaluation_steps=[…], evaluation_params=[SingleTurnParams.…]).
  • Add a Rubric with score bands (0–2, 3–5, 6–8, 9–10) for graded output.
  • Run Correctness + Professional Tone side by side — the notebook's refund-policy cases.

Theory

  • Generation-based evaluation: the judge thinks through steps, then scores.
  • What evaluation_steps and rubrics compile to — they are the prompt.
  • Why G-Eval beats regex/string matching, and when to reach for it.

Module 02 · Days 06–10

The metric toolkit

The built-in metrics, evals as pytest tests, and the two ways to build your own: custom classes and DAG decision trees.

DAY 06

Faithfulness, Hallucination & Answer Relevancy

Code

  • FaithfulnessMetric on answers with and without retrieval_context.
  • HallucinationMetric on an answer that invents facts.
  • AnswerRelevancyMetric on a rambling answer that buries the actual response.

Theory

  • Faithfulness extracts claims from the answer and checks each against the context.
  • Hallucination detects contradictions — the fluent-but-wrong failure mode.
  • Relevancy: how much of the output actually answers the question.
DAY 07

Summarization, JSON & score-only mode

Code

  • SummarizationMetric on long vs short summaries of one text.
  • JsonCorrectnessMetric with expected_schema on valid and malformed JSON.
  • Score-only (threshold=None) and flaky=True metrics — which verdicts get suppressed.

Theory

  • Reference-free metrics: what they compare against when there's no expected output.
  • Flaky metrics score but never decide pass/fail — useful for noisy judges in CI.
  • Every metric's judge prompt can be overridden with evaluation_template.
DAY 08

Evals as tests — pytest + deepeval test run

Code

  • Write tests/test_chatbot.py with assert_test inside plain test functions.
  • Parametrize with @pytest.mark.parametrize over the golden dataset.
  • Run deepeval test run tests/ from the CLI and read the exit code.

Theory

  • Why evals belong in CI: every prompt or model change runs the whole pack.
  • Pytest fixtures: build the judge once per session, reuse across every test.
  • Test hygiene — deterministic cases, small packs, short CI budgets.
DAY 09

Custom metrics

Code

  • Subclass DeepEvalBaseMetric for a deterministic metric (e.g. word-count ceiling).
  • Then a judge-based custom metric using async_mode=True and a_measure().
  • Return self.score, self.reason, and let is_successful() use the threshold.

Theory

  • The metric contract: score + reason + verdict, nothing else.
  • Sync vs async metrics and why custom metrics should be async by default.
  • When to hand-write a metric vs use G-Eval — determinism vs flexibility.
DAY 10

DAG metrics — decision-tree evaluation

notebook · DAG section (incl. its 2 bug patches)

Code

  • Build DAGMetric from TaskNode → BinaryJudgementNode → VerdictNode.
  • The notebook's heading-order example: extract headings, gate on presence, then score order.
  • Reuse the notebook's two monkey-patches if your DeepEval version hits the DAG template bugs.

Theory

  • When criteria are a procedure, not prose — DAG encodes branching logic.
  • Node types: tasks extract, judgements gate, verdicts score — and how scores flow down branches.
  • DAG vs G-Eval: objective or mixed criteria belong in a graph, not a prompt.

Module 03 · Days 11–16

RAG evaluation

The heart of the course. Students build a small RAG, measure its retriever and generator separately with DeepEval's five RAG metrics, then improve it against the scores.

DAY 11

Anatomy of a RAG you can evaluate

notebook · RAG section

Code

  • A tiny 5-document corpus (tokens, embeddings, RAG, hallucination, agents).
  • A naive keyword-overlap retriever returning top-k chunks.
  • A Groq answer function with the "answer ONLY using the provided context" prompt.

Theory

  • Index → retrieve → generate: three components, three failure points.
  • Why retrieval and generation must be evaluated separately.
  • Golden datasets for RAG: question + expected answer + which docs should come back.
DAY 12

Contextual Precision — is the ranking right?

Code

  • ContextualPrecisionMetric on retrieved node lists.
  • Inspect verbose_logs to see the judge walk node by node.
  • Compare: correct chunk first vs correct chunk buried at position 3.

Theory

  • Precision is about order: the answer may be in there, but does it rank first?
  • How the judge scores each node against the question and prior nodes.
  • Why ranking matters — top-k truncation silently drops lower nodes.
DAY 13

Contextual Recall & Relevancy

Code

  • ContextualRecallMetric with expected_output as the answer to cover.
  • ContextualRelevancyMetric — add a noise doc and watch the score drop.
  • Run all three retriever metrics on the same cases in one evaluate().

Theory

  • Recall: is the information needed to produce the expected answer anywhere in the nodes?
  • Relevancy: signal-to-noise — how many retrieved chunks are actually used?
  • Reading recall and precision together: coverage vs ranking are different diseases.
DAY 14

Generator metrics — Faithfulness & Answer Relevancy

Code

  • Generate real answers with the Day-11 pipeline for the three notebook questions.
  • FaithfulnessMetric and AnswerRelevancyMetric on each answer.
  • Watch the out-of-corpus Docker question — the model should refuse, not invent.

Theory

  • Grounding: faithfulness checks the answer against retrieved context only.
  • Helpfulness: relevancy checks the answer against the question.
  • What the "answer only from context" prompt does to both scores — and why refusal is correct behavior.
DAY 15

The full RAG report

notebook · RAG section (the 5-metric run)

Code

  • Run all five RAG metrics together — ~41 judge calls on 3 cases.
  • Add AsyncConfig(max_concurrent, throttle_value) and ErrorConfig(skip_on_missing_params=True).
  • Write a one-paragraph failure analysis for each failing case.

Theory

  • Diagnosing failures: is it the retriever (precision/recall) or the generator (faithfulness/relevancy)?
  • Mapping scores to fixes — a recall problem is chunking, a relevancy problem is the query.
  • Why the notebook's token question failed: keyword overlap can't do semantics.
DAY 16

Evaluation-driven RAG improvements

Code

  • Replace the keyword retriever with embedding similarity (or tune k).
  • Re-run the Day-15 suite; diff average scores and pass rates before/after.
  • Add 3 new questions to the golden set and re-evaluate both retrievers.

Theory

  • The optimize loop: hypothesis → change → re-evaluate → keep or revert.
  • Synthetic test generation: derive new test cases from your own documents.
  • Regression packs — the old suite is the safety net for every improvement.

Module 04 · Days 17–24

Agents & multi-agent systems

Non-deterministic agents need traces before metrics. Students build a tool-using agent, evaluate its tool calls and its full trajectory, then extend to multi-turn and multi-agent systems.

DAY 17

LLM tracing

Code

  • @observe(type="tool") on a function; call it and print the trace tree.
  • Wrap a whole run in trace() and inspect root_spans.
  • Set CONFIDENT_TRACE_VERBOSE=0 to silence dev logging.

Theory

  • Spans and traces: every tool call, prompt, and output as a tree.
  • Why agents need traces before metrics — two identical answers can hide very different runs.
  • Tracing = observability for non-deterministic systems.
DAY 18

Build a tool-using agent

notebook · Agent section

Code

  • Three @tools: search_docs, run_code, escalate_to_human — each wrapped in @observe.
  • LangChain create_agent(llm, tools, system_prompt) with ChatGroq.
  • Run it: "run print(2**10)" should call exactly one tool.

Theory

  • The agent loop: plan → act (call a tool) → observe → decide → repeat.
  • Tool schemas are the agent's action space; descriptions are its only documentation.
  • Frameworks: LangChain, LangGraph, Pydantic AI — DeepEval works with all of them.
DAY 19

Traces → agent test cases

notebook · Agent section

Code

  • Run the agent on 3 tasks; capture tools_called and the trace dict per run.
  • Build LLMTestCases with expected_tools=[ToolCall(name=…)].
  • Attach the trace via test_case._trace_dict = … — trajectory metrics need it.

Theory

  • What a trajectory test case needs: the output, the tool calls, and the full trace.
  • expected_tools encodes intent — "this task should need a docs search".
  • Capturing traces programmatically so evals run anywhere, not just in the notebook.
DAY 20

Action metrics — judging single tool calls

Code

  • ToolCorrectnessMetric on the 3 cases — right tool for the intent?
  • ArgumentCorrectnessMetric — right arguments for that tool?
  • Check verbose_logs to see which call each score is judging.

Theory

  • Component-level evaluation: judge one decision at a time, not the whole run.
  • Why actions are judged before outcomes — a right answer reached by the wrong path is still a bug.
  • Tool correctness catches the escalate-vs-search mistakes no output metric can see.
DAY 21

Trajectory metrics — judging the whole run

Code

  • TaskCompletionMetric — did the goal get reached?
  • PlanAdherenceMetric + PlanQualityMetric — was the plan good, and was it followed?
  • StepEfficiencyMetric — were the steps economical?

Theory

  • A trajectory is the ordered chain of decisions — right tools in the wrong order is still a failure.
  • Completion scores the destination; adherence, quality, and efficiency score the path.
  • Why one metric is never enough for an agent — read the four together.
DAY 22

The full agent report

notebook · Agent section (the 6-metric run)

Code

  • Run all six agent metrics in one evaluate() with a light throttle (~18 judge calls).
  • Analyze the notebook's failure: 9× search_docs calls for one question.
  • Fix it — cap iterations or improve tool descriptions — and re-run to show the delta.

Theory

  • Reading agent failures: tool choice (Day 20) vs plan vs efficiency (Day 21).
  • Loop bugs are efficiency failures — tracing them to fixes like max-iteration caps.
  • The complete agent harness is a template: swap the agent, keep the suite.
DAY 23

Multi-turn chatbots

Code

  • Build ConversationalTestCase with a messages list.
  • KnowledgeRetentionMetric and RoleAdherenceMetric on a forgetful bot.
  • ConversationCompletenessMetric + ConversationRelevancyMetric on the same dialogue.

Theory

  • Conversations are evaluated as a whole, not turn by turn.
  • Memory metrics: did the bot keep facts from turn 1, and stay in character?
  • When a chatbot suite beats single-turn cases — any app with session state.
DAY 24

Multi-agent systems

new material — extends the notebook

Code

  • A small LangGraph setup: supervisor agent + one worker agent with its own tools.
  • Trace the whole system; identify each sub-agent's spans in the tree.
  • Evaluate end-to-end, then attach component metrics per agent span for blame attribution.

Theory

  • What multi-agent adds: handoffs, parallel workers, separation of roles — and new failure modes.
  • Evaluate each agent in isolation and end-to-end; the handoff itself is testable.
  • Traces make blame attribution possible — which agent broke the chain?

Module 05 · Days 25–28

Production & beyond

Safety guardrails, benchmarks, CI integration, and the platform layer. The course ends with a capstone: one end-to-end suite for everything built so far.

DAY 25

Safety metrics

Code

  • BiasMetric, ToxicityMetric, MisuseMetric on adversarial cases.
  • NonAdviceMetric (medical/legal) and PIILeakageMetric with a fake dataset.
  • RoleViolationMetric — the bot must stay a bot.

Theory

  • Guardrail evals: safety scores are separate from quality scores and gate separately.
  • Adversarial packs stay red-team-style, out of the main golden dataset.
  • Thresholds here are policy decisions, not accuracy targets.
DAY 26

Benchmarks & multimodal

Code

  • Run a small HellaSwag subset via deepeval.benchmarks.
  • One ImageCoherenceMetric case with MLLMImage.
  • Compare the benchmark score with your own suite's score on the same model.

Theory

  • Public benchmarks measure the model, not your app — both matter, never conflate them.
  • What benchmarks hide: your prompts, your context, your users.
  • The image metric family (coherence, helpfulness, reference, editing) and when multimodality enters evals.
DAY 27

Evals in production

Code

  • Export and import the course's test cases as a dataset (.json round-trip).
  • A GitHub Actions step running deepeval test run tests/ on every PR.
  • Log hyperparameters (prompt version, model, temperature) alongside each run.

Theory

  • Regression packs: the suite is a contract — any change that drops it gets caught.
  • CI gates with flaky metrics, budgets, and caching judges.
  • Track cost and latency next to scores — a 2% quality win that doubles cost is a decision.
DAY 28

Capstone + Confident AI

notebook · deepeval view cell

Code

  • Assemble everything into one end-to-end suite: RAG pipeline + agent + safety pack.
  • deepeval view to push results to Confident AI and open the dashboard.
  • Students demo: a failing case, its trace, its fix, and the green re-run.

Theory

  • The full loop: build → evaluate → trace → fix → ship → watch.
  • Confident AI: dashboards, regression testing, and team-wide visibility of scores.
  • Next step: red teaming with DeepTeam — evals find bugs, red teaming finds the bugs you didn't think to test.

Notebook map

  • G-Eval section → Days 03–05: the Groq judge and both G-Eval metrics are reused almost every day after.
  • DAG section → Day 10: keep the two monkey-patches with it — some DeepEval versions still need them.
  • RAG section → Days 11–15: corpus, retriever, pipeline, and the 5-metric run map one-to-one.
  • Agent section → Days 17–22: tools, create_agent, traces, and the 6-metric run.
  • Define the judge once on Day 3 (llama-3.3-70b-versatile via Groq) and import it everywhere.

Teaching tips

  • Every day ends with at least one failing case — students read the reason before they touch a fix.
  • Keep one golden dataset growing from Module 03 onward; it becomes the capstone's regression pack.
  • Stay on the tiny 5-doc corpus and light throttles — the whole course runs on a free Groq key.
  • Days 16 and 22 are the payoff days: change one thing, watch the scores move, explain why.
